# Handoff hardening guards

Runnable local guard modules embedded in `../Proofs.txt` (hardening batches P1-P10 … P141-P150, P151-P160, P161-P170, P171-P180, P181-P190, P191-P200) together with their evidence files. Each module's SHA256 and byte count are recorded in `Proofs.txt` next to its embedded copy; each evidence file records the `source_sha256` of the module that produced it and, from v2 on, the `dependency_sha256` of the modules it imports.

Cross-runtime oracle for recurrence: `rrule_oracle.php` expands an RRULE with php-rrule (https://github.com/rlanvin/php-rrule, commit 93a083db12dcb6f58e4840392a22e158ce96f1ff, cloned to /home/user/rlanvin/php-rrule) under PHP 8.4.19. php-rrule documents itself as having started as a port of python-dateutil, so its agreement corroborates the dateutil lineage in a second runtime rather than an independent reading of RFC 5545; the tests say so. Cross-runtime oracles for month arithmetic: `month_offset_oracle.rb` shifts a date by whole months with Ruby's `Date#>>` under ruby 3.3.6, and `month_offset_oracle.php` applies one relative modifier with `DateTime::modify` under PHP 8.4.19. Both are C implementations in their own standard libraries, unrelated to python-dateutil. Ruby's behaviour was read in `ext/date/date_core.c` at tag `v3_3_6`; PHP's was read in a clone of https://github.com/php/doc-en at commit `d8de774ae203bccf3ffe02895d8c8fc754377451` (`reference/datetime/datetime/modify.xml` and `reference/datetime/formats.xml`). Each shim parses argv, calls the library and prints one ISO date; every value compared on the Python side comes from `subprocess` output. The same two shims answer the later tests that compose and reverse an offset, which call them two, three or four times per example and therefore run under a smaller `hypothesis` settings profile than the rest of the file. The month-arithmetic tests that call a shim skip cleanly when the runtime is absent; the rest compare pandas with dateutil inside Python. The PHP shim takes any relative modifier, so the month-end tests added later ask it for "last day of this month" and compare that with `Period.end_time`; the two further implementations of the month end run in process and need no shim, polars 1.44.1's `dt.month_end`, read in `py-polars/src/polars/expr/datetime.py` at tag `py-1.44.1`, and DuckDB 1.5.5's `last_day`, read in the duckdb-web checkout at commit `6f6cd1659f0e2ddd1965b1d3f1833e7fc512e7ac`.

Cross-runtime oracles for case folding: `case_fold_oracle.rb` prints Ruby 3.3.6's `String#downcase(:fold)` and `String#downcase` of one string, and `case_fold_oracle.php` prints PHP 8.4.19's `mb_convert_case(..., MB_CASE_FOLD, 'UTF-8')` and `mb_strtolower(..., 'UTF-8')`. Second implementation for the Beancount journal format: `beancount-parser-lima` 0.6.0, a Rust parser installed as a wheel and imported directly, so there is no shim. The reader is `junitparser` 5.0.3, newly pinned in `requirements-hardening.txt`; its published metadata at that version declares no runtime dependencies, it parses the XML itself rather than wrapping pytest, and it was read at tag `v5.0.3` in `src/junitparser/junitparser.py`, where `result` is "A list of :class:`Failure`, :class:`Skipped`, or :class:`Error` objects" and `is_passed` is "Whether this testcase was a success (i.e. if it isn't skipped, failed, or errored)." The naive rule the case writes as a loop is expressed in the tests as libxml2's XPath `testcase[not(failure)]`, so both readings come from libraries and neither is written here. Each of the six tests runs pytest in a subprocess over generated test modules, which costs about half a second a call, so they run at a new profile `REPORT_RUN` (12 examples).

Running the pytest file across several CPUs. `pytest-xdist` 3.8.0, with `execnet` 2.1.2 beneath it, is pinned in `requirements-hardening.txt` and is a runner rather than an oracle: it changes nothing any test asserts. Its `docs/distribution.rst` at tag `v3.8.0` documents the option this repository uses -- "To send tests to multiple CPUs, use the ``-n`` (or ``--numprocesses``) option", "Pass a number, e.g. ``-n 8``, to specify the number of processes explicitly", and "Use ``-n 0`` to disable xdist and run all tests in the main process". Four is the number of CPUs here. Each worker is a separate process, which matters for exactly one test in the file: `test_the_module_grid_reads_process_state_that_the_object_grid_declares` calls `calendar.setfirstweekday`, the only interpreter-wide state any test touches, and restores it in a `finally`, so it is confined to its own worker either way. If a test ever fails under `-n 4` and passes without it, that difference is itself a finding and belongs in the register; nothing may be relaxed to make a parallel run pass.
