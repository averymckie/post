# Handoff hardening guards

Runnable local guard modules embedded in `../Proofs.txt` (hardening batches P1-P10 … P141-P150, P151-P160, P161-P170, P171-P180, P181-P190, P191-P200) together with their evidence files. Each module's SHA256 and byte count are recorded in `Proofs.txt` next to its embedded copy; each evidence file records the `source_sha256` of the module that produced it and, from v2 on, the `dependency_sha256` of the modules it imports.

Cross-runtime oracle for recurrence: `rrule_oracle.php` expands an RRULE with php-rrule (https://github.com/rlanvin/php-rrule, commit 93a083db12dcb6f58e4840392a22e158ce96f1ff, cloned to /home/user/rlanvin/php-rrule) under PHP 8.4.19. php-rrule documents itself as having started as a port of python-dateutil, so its agreement corroborates the dateutil lineage in a second runtime rather than an independent reading of RFC 5545; the tests say so. Cross-runtime oracles for month arithmetic: `month_offset_oracle.rb` shifts a date by whole months with Ruby's `Date#>>` under ruby 3.3.6, and `month_offset_oracle.php` applies one relative modifier with `DateTime::modify` under PHP 8.4.19. Both are C implementations in their own standard libraries, unrelated to python-dateutil. Ruby's behaviour was read in `ext/date/date_core.c` at tag `v3_3_6`; PHP's was read in a clone of https://github.com/php/doc-en at commit `d8de774ae203bccf3ffe02895d8c8fc754377451` (`reference/datetime/datetime/modify.xml` and `reference/datetime/formats.xml`). Each shim parses argv, calls the library and prints one ISO date; every value compared on the Python side comes from `subprocess` output. The same two shims answer the later tests that compose and reverse an offset, which call them two, three or four times per example and therefore run under a smaller `hypothesis` settings profile than the rest of the file. The month-arithmetic tests that call a shim skip cleanly when the runtime is absent; the rest compare pandas with dateutil inside Python. Cross-runtime oracles for case folding: `case_fold_oracle.rb` prints Ruby 3.3.6's `String#downcase(:fold)` and `String#downcase` of one string, and `case_fold_oracle.php` prints PHP 8.4.19's `mb_convert_case(..., MB_CASE_FOLD, 'UTF-8')` and `mb_strtolower(..., 'UTF-8')`. Cross-runtime oracles for the calendar date a record denotes: `iso_date_oracle.rb` reads one date or timestamp with Ruby 3.3.6's `Date.parse` and prints the calendar date and that date's Julian day number, and `iso_date_oracle.php` reads the same text with PHP 8.4.19's `DateTimeImmutable` and prints the calendar date and `getTimestamp()`. The second line is what lets the tests take an ordering from each runtime instead of comparing text again: `Date#jd` is documented in `ext/date/date_core.c` at tag `v3_3_6` as "Returns the Julian day number", and `DateTimeInterface::getTimestamp` in the doc-en checkout at `reference/datetime/datetimeinterface/gettimestamp.xml` as "Gets the Unix timestamp". `Date.parse` is documented at the same tag as a method that "recognizes many forms in +string+, but it is not a validator", which is why it reads the unpadded record the tests generate. Each shim parses argv, calls the library and prints two lines; the Python side runs `subprocess` and splits stdout. The four tests that call them skip cleanly when either runtime is absent.

Third implementation of Unicode normalization: `unicode_normalize_oracle.rb` normalizes one string with Ruby 3.3.6's `String#unicode_normalize` and prints the normalized text, its length in characters and its length in bytes. Ruby's implementation is neither ICU nor CPython's: it is written in Ruby, in `lib/unicode_normalize/normalize.rb` and its generated `tables.rb` at tag `v3_3_6`, whose header records that they "are part of the implementation of the built-in String class, not part of the standard library". The second implementation in this cluster runs in process: polars' `str.normalize`, which is the Rust `unicode-normalization` crate declared in `crates/polars-ops/Cargo.toml` at tag `py-1.44.1`. Text crosses into and out of the shim as hex, so the shim's only work is one decode, one library call and three prints, and nothing depends on the reader's locale -- the defect the case-folding shim above had to work around cannot arise here. The five normalization tests that call it skip cleanly when ruby is absent; four more compare CPython with polars and with rapidfuzz inside Python.

Second implementation of HTML parsing: `html5lib` 1.1, imported directly, so there is no shim. Its README at tag `1.1` calls it "a pure-python library for parsing HTML" that "is designed to conform to the WHATWG HTML specification, as is implemented by all major web browsers", and its `setup.py` at that tag declares `six>=1.9` and `webencodings` as `install_requires`; `lxml` appears only under `extras_require`, and the tests ask for the `etree` treebuilder, so none of libxml2 is under it. Independent writers and readers of the ZIP container: `zip_package_oracle.java` reads one archive with `java.util.zip` under OpenJDK 21.0.10, prints one tab-separated line per entry -- the name as hex, the six components of `ZipEntry.getTimeLocal`, the storage method, the size and the CRC-32 -- and then writes a second archive holding the same entries, stored, under the same names in the same order with the same MS-DOS local date-times; `zip_stamp_oracle.php` reads the same archive with PHP 8.4.19's `ZipArchive`, which is libzip 1.7.3, and prints each entry's name as hex and the last-modified instant that runtime resolves it to. Neither shares code with `repro-zipfile` 0.4.1 or with CPython's `zipfile`: `java.util.zip` is part of the OpenJDK class library, read in `src/java.base/share/classes/java/util/zip/ZipEntry.java` and `ZipOutputStream.java` at tag `jdk-21.0.10-ga`, and libzip is a C library read in `lib/zip_dirent.c` at tag `v1.7.3`, reached from PHP through the `statIndex` macro in `ext/zip/php_zip.c` at tag `php-8.4.19`, which copies libzip's own `mtime` out unchanged. Go's `archive/zip` is a third independent implementation of the same format; it was found by the rule 2a search and recorded rather than used, because these two already answer every claim in the cluster. Both shims parse argv, call the library and print; the Python side writes the archive to a temporary file, runs the shim in a named zone through the `TZ` environment variable and splits stdout. The zone matters and is part of what the tests establish: `ZipEntry.getTimeLocal` reads the MS-DOS fields directly and is zone-free, while libzip's `_zip_d2u_time` ends in `mktime(&tm)` and is not. Java runs its shim as a single-file source program, so there is no build step and no compiled class in this repository, and no jars are needed; the nine tests that call the two shims skip cleanly when java or php is absent.

Second implementations for the chart axis and for the workbook table, none of which needs a shim beyond one already here. matplotlib 3.11.1 turns a date into a day number with `date2num`, read in `lib/matplotlib/dates.py` at tag `v3.11.1`; the two independent numberings it is checked against are the standard library's `date.toordinal`, which counts from a different origin and is not matplotlib's code, and Ruby 3.3.6's `Date#jd` through the existing `iso_date_oracle.rb`, whose second printed line is that Julian day number. No independent implementation of a rectangle's extents was sought, because none is needed: `broken_barh`, whose signature at the same tag is a "sequence of tuples (*xmin*, *xwidth*)", is asked for the width of an interval whose length the strategy generated, so the expected value is an invariant of the input. Matplotlib is used with the `Agg` backend, set once at import, so the chart tests draw without a display. For XlsxWriter 3.2.9's `add_table`, read in `xlsxwriter/worksheet.py` at tag `RELEASE_3.2.9`, the second implementations are readers rather than writers, because the claim is about what one writer leaves in the file: openpyxl 3.1.5 and the Rust calamine reader through python-calamine 0.8.2 return the same grid for every generated schedule. The one test that calls the ruby shim skips cleanly when ruby is absent; the other seven run in process.

Second and third implementations of the list-to-rows reshaping, both in process, so there is no shim. pandas 2.2.3's `DataFrame.explode` was read in `pandas/core/frame.py` at tag `v2.2.3`; DuckDB 1.5.5's `UNNEST` answers the same question in SQL and shares nothing with either dataframe library; polars 1.44.1's `explode` was read in `py-polars/src/polars/dataframe/frame.py` at tag `py-1.44.1`, where `empty_as_null` and `keep_nulls` are documented separately and are exactly what makes it agree with one engine or the other. Second and third implementations of the pivot, both in process and needing no shim. pandas 2.2.3's `DataFrame.pivot` was read in `pandas/core/frame.py` at tag `v2.2.3` and the error it raises for a repeated pair in `pandas/core/reshape/reshape.py` at the same tag; polars 1.44.1's `pivot`, including the `aggregate_function` and `sort_columns` arguments the divergences turn on, was read in `py-polars/src/polars/dataframe/frame.py` at tag `py-1.44.1`; DuckDB 1.5.5's `PIVOT` statement, whose `USING` clause is mandatory in effect because it defaults to `count(*)`, was read in the duckdb-web checkout at commit `6f6cd1659f0e2ddd1965b1d3f1833e7fc512e7ac` (`docs/current/sql/statements/pivot.md`). Second and third implementations of the character-to-glyph mapping a chart's SVG is written with. matplotlib 3.11.1 saves an SVG under the shipped `svg.fonttype: path`, documented in `lib/matplotlib/mpl-data/matplotlibrc` at tag `v3.11.1` as "path: Embed characters as paths", and names each glyph with the identifier `TextToPath._get_glyph_repr` builds in `lib/matplotlib/textpath.py` at that tag, `urllib.parse.quote(f"{font.postscript_name}-{glyph:x}")`, from a glyph index FreeType supplies through `matplotlib.ft2font`. The two readers of the same DejaVuSans.ttf that check those identifiers are not FreeType. fontTools 4.64.0 runs in process and needs no shim: `getGlyphOrder`, "Returns a list of glyph names ordered by their position in the font.", and `getBestCmap` were read in `Lib/fontTools/ttLib/ttFont.py` at tag `4.64.0`. fontTools is named in matplotlib's own dependencies at `v3.11.1` ("fonttools >= 4.28.2" in `pyproject.toml`), so the outside reader is the second one: `glyph_index_oracle.js` maps each character of one string to a glyph index with opentype.js 2.0.0 under node v22.22.2 and prints one index per line. Its `package.json` at tag `2.0.0` declares no runtime dependencies at all -- only mocha, esbuild and eslint under `devDependencies` -- and calls it an "OpenType font parser"; `Font.prototype.charToGlyphIndex` is documented in `src/font.mjs` at that tag as "Convert the given character to a single glyph index." The text crosses into the shim as hex, so the shim's only work is one decode, one library call and one print per character. Install it outside this repository and point the tests at it: `npm install --prefix ~/opentype-oracle opentype.js`, or set `OPENTYPE_DIR` to another prefix; the one test that calls it skips cleanly when node or the checkout is absent. One pair of characters escapes that mapping and is the subject of its own test: matplotlib substitutes a ligature for `ff`, `fi` and `fl`, so the file holds one `<use>` element where the cell holds two characters. Which pairs those are is read off matplotlib at import over the candidates `unicodedata.decomposition` names -- the thirteen characters DejaVu Sans carries that decompose into two characters of the cell alphabet -- and the glyph written is checked against the index the font's own cmap gives the single Unicode character naming that ligature, so nothing about the substitution is typed. opentype.js cannot corroborate that one: asked to shape a string rather than to map a character it refuses this font outright, and `stringToGlyphs` raises `Error: substitutionType : 62 lookupType: 6 - substFormat: 2 is not yet supported` for any text, which is why the shim maps characters and nothing more. The other twelve tests in that cluster run in process and read the SVG twice, with libxml2 through `lxml` and with expat through `xml.etree.ElementTree`, comparing the two readings before using either; the reproducibility half of the cluster compares sha256 digests of two saves of the same generated figure, which is an invariant of matplotlib's own output and needs no oracle, and the instant that `SOURCE_DATE_EPOCH` puts in the file is checked against the one pandas resolves that epoch to in UTC.

A second implementation of the QR format, in process and needing no shim. segno 1.6.6 writes the code and OpenCV 5.0.0, shipped here as `opencv-python-headless` 5.0.0.93, reads it with the two detectors the case uses.
